# JWT（JSON Web Token）

HTTP 是无状态协议 — 每次请求都是独立的，服务器不会记住你是谁。但应用需要知道「你是谁」，这就是认证要解决的根本问题。

最早的解法是 Session。服务器在内存里开一块空间记住你，给你一个 session_id 带回去，下次带上就认识你了。单机时代完美运行。

但服务器变成集群后问题来了：session 存哪？每台机器都存一份？还是搞个共享存储？不管哪种方案，都引入了状态同步的复杂性 — 你要么接受单点故障（只存一台），要么接受同步开销（存共享缓存），要么接受不一致（每台都存但可能对不上）。

这个矛盾的根源在于：服务器在「记住」用户。如果服务器不记住任何人呢？

这就是无状态认证的思路 — 让客户端自己证明「我是谁」。服务器不需要存任何东西，只需要验证客户端带来的凭证是否合法。

JWT 就是这个思路的具体实现。它把你需要的信息（用户 ID、角色等）编码成 JSON，然后用密钥签名，变成一个字符串。客户端每次请求带上这个字符串，服务器用密钥验签名，签名对了就信任里面的数据。

因为验证只需要密钥（不需要查数据库或共享存储），所以任何一台服务器都能独立验证，天生适合分布式。这也是 JWT 名字里 "JSON" 的由来 — 载荷就是 JSON。

但 JWT 有一个代价：一旦签发就无法撤销。它不像 session 可以直接删掉服务端记录，JWT 在过期之前一直有效。这意味着如果有人偷了你的 JWT，在过期之前他一直可以冒充你。

双 Token 机制就是为了缓解这个问题：把 JWT 的有效期压到很短（30分钟），同时用一个可撤销的长效令牌（refresh_token）来续期。这样即使 access_token 被盗，30 分钟后自动失效；而 refresh_token 存在数据库里，发现异常可以随时撤销。

所以 JWT 的本质是：用「签名验证」替代「服务端存储」，用「短寿命 + 可撤销的长寿命令牌」来平衡安全性和可用性。它解决的核心问题是分布式系统中认证状态的管理。
