# 上下文截断策略

截断不是可选的优化，而是所有 LLM 对话系统的必然约束。三种经典策略——全量保留、滑动窗口、摘要压缩——各自解决的其实是「信息丢失的不同形态」：全量保留丢失的是预算，滑动窗口丢失的是远期上下文，摘要压缩丢失的是细节保真度。生产环境不存在万能策略，选型的核心是搞清楚你的对话场景**不能丢什么**。

## 为什么截断不可避免

LLM 的上下文窗口是硬性 token 预算。即使 GPT-4o 拥有 128K context window，一个持续运行的生产对话系统仍然会撞墙——不是因为单轮太长，而是因为**对话轮次无限累积**。

README 中将这个问题归结为第一阶段的核心困境：「上下文窗口有限（token budget），对话越来越长怎么办？删哪些、留哪些？」这是所有 Memory 抽象的底层动因。LangChain 提供 `trim_messages`，Vercel AI SDK 提供 `maxSteps`，OpenAI SDK 则什么也不提供——它只负责把 messages 数组发出去，超了就报错。截断的责任完全在调用方。

token 预算的真正压力来自三个容易被低估的来源：

1. **系统 prompt + few-shot 示例**往往占据 2K-10K token，还没开始对话就已消耗大量预算
2. **工具调用的往返**（README 第四阶段）每次往返动辄数百 token，一个 Agent 会话可能产生几十次工具调用
3. **多模态内容**（图片、文件）的 token 消耗远高于纯文本

所以截断策略不是「需不需要」的问题，而是「用什么方式丢」的问题。

## 三种策略的真实代价

README 第二阶段将框架的 Memory 抽象归纳为三种策略。教科书式的优缺点分析（省 token vs 丢上下文）没有实际指导意义。真正有用的是理解**每种策略在什么时候会崩**。

### 全量保留（ConversationBufferMemory）

把所有历史消息原封不动地拼入 prompt。

**什么时候有效**：短对话（10 轮以内）、token 预算充裕的场景（长 context 模型 + 简单问答）。

**什么时候失败**：当对话持续足够长，token 总量超过模型上下文窗口，API 调用直接报错。不是「效果变差」，而是**完全不可用**。OpenAI 返回 `context_length_exceeded` 错误，整个对话中断。

这是最容易被忽视的一点：全量保留策略**没有优雅降级路径**。它从「一切正常」直接跳到「彻底崩溃」，中间没有过渡态。在 mastery 文档的 OpenAI 实现中，`sessions[session_id]` 无限追加消息，没有任何截断逻辑——如果用户持续对话，这个系统必然在某一次请求时崩溃。

**真实成本**：token 费用线性增长（每轮请求都发送全部历史），且越长越慢（推理时间随 input token 增长）。

### 滑动窗口（ConversationBufferWindowMemory）

只保留最近 N 轮对话，丢弃更早的消息。

**什么时候有效**：问答型场景、闲聊、当前问题不依赖早期上下文的任务。

**什么时候失败**：当用户在**第 3 轮说了关键前提，第 15 轮才用到它**。滑动窗口会毫不犹豫地丢掉第 3 轮的消息。典型场景：

- 用户开头说「我在用 Python 3.8」，后面所有代码生成依赖这个版本约束
- 用户在早期设定了偏好（「用中文回答」），窗口滑动后偏好丢失
- 多步骤任务中的计划或决策被截断，后续执行失去目标

**隐蔽的失败模式**：滑动窗口不会报错。它会静默地丢失上下文，然后 LLM 基于不完整的信息生成一个**看似合理但完全错误**的回答。这比报错更危险——用户可能不会察觉信息缺失，直到产生实际后果。

LangChain 的 `trim_messages` 实现中，`strategy="last"` 配合 `max_tokens` 就是滑动窗口的变体，但它是按 token 数而非轮数截断，粒度更细，本质问题不变。

### 摘要压缩（ConversationSummaryMemory）

用 LLM 将旧对话压缩为摘要文本，替换原始消息。

**什么时候有效**：长对话、需要保留整体脉络的场景（咨询、分析、持续协作）。

**什么时候失败**：见下一节的详细分析。

**真实成本**：每次生成摘要都是一次额外的 LLM 调用。这意味着：
- 每次截断触发时多付一次 API 费用
- 增加延迟（摘要生成需要时间）
- 摘要本身也消耗 token，且质量高度依赖摘要 prompt 的设计

## 摘要的隐藏陷阱：信息丢失是非均匀的

摘要策略最大的问题不是「丢失信息」，而是**丢失的信息不可预测且不均匀**。

考虑一段 20 轮的对话：用户讨论了一个技术方案，前 5 轮探索了三个候选方案并选择了方案 B，中间 10 轮讨论了方案 B 的实现细节，最后 5 轮测试并修复了两个 bug。

摘要 LLM 会怎么做？大概率会重点概括「最终选择了方案 B」和「修复了哪些 bug」，因为摘要模型倾向于保留结论和结果。但真正关键的可能是**为什么否决了方案 A 和 C**——这些「被否决的理由」在后续讨论中不会反复提及（因为已经决定了），却是理解系统设计意图的关键上下文。

信息丢失的非均匀性体现在三个维度：

**1. 否决信息优先丢失**

摘要模型保留「做了什么决定」，丢失「为什么不做另一个决定」。但否定性信息（为什么不用 X）往往比肯定性信息（用了 Y）更具约束力——它划定了设计空间的边界。

**2. 细节数量与重要性无关**

一段 200 token 的代码片段和一段 200 token 的需求讨论，在摘要中被压缩为大致相同长度的概括。但代码片段可能是关键约束（「这里必须用同步 IO」），而需求讨论可能只是背景铺垫。摘要不区分信息的「密度」。

**3. 指代关系被破坏**

原始对话中的「就用刚才说的那个方案」在摘要后变成无解的指代——「刚才说的那个方案」的原文已经被压缩掉了。摘要后的消息引用摘要内容，但摘要可能没有保留原始消息的指代锚点。

**生产建议**：如果使用摘要策略，摘要 prompt 应该显式要求保留「被否决的选项及原因」和「关键约束条件」。不要指望摘要模型自动判断什么重要。

## 生产环境选型指南

不要选「最好的策略」，选「你扛得住哪种失败」。

| 策略 | 失败形态 | 你能接受吗？ | 适合场景 |
|---|---|---|---|
| 全量保留 | 突然报错，对话中断 | 可以中断，但不能出错 | 短会话工具（CLI 助手、一次性任务） |
| 滑动窗口 | 静默丢失早期上下文 | 当前任务不依赖远期信息 | 问答机器人、闲聊、客服 |
| 摘要压缩 | 信息非均匀丢失 | 需要整体脉络但不依赖细节 | 长期协作、咨询、分析 |

**实际建议**：

1. **大多数场景用滑动窗口，设定合理的 token 上限**。简单、可预测、失败模式透明。LangChain 的 `trim_messages` 或 OpenAI SDK 中手动截断都可以。

2. **如果对话中存在「设定阶段」**（用户开头说明需求、约束、偏好），将设定信息提取为 system prompt 的一部分，不参与窗口滑动。这比摘要策略更可靠——system prompt 是固定保留的。

3. **只在对话确实很长且需要长期记忆时考虑摘要**。摘要的额外成本（API 调用 + 信息丢失风险）只有在滑动窗口完全不可用时才值得承担。

4. **混合策略是最务实的选择**：system prompt 保留固定设定 + 滑动窗口保留近期对话 + 可选地对关键转折点做选择性摘要。不需要框架的复杂抽象，手动实现反而更容易控制和调试。

5. **始终设置 token 预算监控**。无论用什么策略，在发送请求前计算 token 数，接近上限时主动告警或切换策略，而不是等到 API 报错。
