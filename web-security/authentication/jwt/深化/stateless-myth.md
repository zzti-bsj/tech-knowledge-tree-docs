# JWT 的「无状态」在生产中真的成立吗？

不完全成立。JWT 的**验证过程**确实是无状态的——任何持有密钥的服务器都能独立验证签名，不需要查数据库。但一个完整的 JWT 认证**系统**在生产中几乎不可避免地引入状态。关键在于区分「token 验证」和「认证系统」。

## 无状态成立的部分

README 中说的「用签名验证替代服务端存储」在验证环节是真的。服务器收到 JWT 后：

1. 用密钥验签名 → 确认没有被篡改
2. 检查 `exp` → 确认没有过期
3. 读取 `sub` → 知道是谁

全程零数据库查询，零网络调用。在纯粹「发 token → 验 token」的流程中，确实无状态。这也是 JWT 在微服务网关层做验证的优势——网关不需要连接用户数据库，只需要密钥。

## 无状态崩溃的三个场景

### 1. Token 撤销

README 指出「JWT 一旦签发就无法撤销」，这是无状态的代价。但生产中你必须处理这些情况：

- 用户改了密码，旧的 token 应该立即失效
- 管理员封禁了某个用户
- token 被发现泄露

解决方案无一例外引入状态：

| 方案 | 引入的状态 | 代价 |
|---|---|---|
| Token 黑名单 | 每次撤销存一条记录 | 每次验证都要查黑名单 |
| 缩短 access_token 寿命 | 状态减少 | 刷新更频繁 |
| 双 token + DB 存储 refresh_token | refresh_token 的存储和查询 | 参见 dual-token【RLSys】.md |

dual-token 方案其实是把「无状态」的范围缩小了——access_token 依然无状态验证，但 refresh_token 是有状态的（存数据库，可撤销）。这是一种务实的折中：高频请求（验证 access_token）保持无状态的性能优势，低频操作（刷新 token）接受有状态以获得可控性。

### 2. 用户信息变更

JWT 的 payload 在签发时就固定了。如果用户的角色从 `user` 变成 `admin`，已经签发的 token 里还是 `user`。要让它生效，只有两条路：

- 等旧 token 过期，重新签发（有延迟）
- 主动撤销旧 token，强制重新登录（又引入状态）

这不是 JWT 的 bug，而是「token 即数据」这种设计的固有约束。payload 越多（角色、权限、组织），这个问题越严重。

### 3. 密钥轮换

更换签名密钥时，用旧密钥签发的 token 怎么办？两种策略：

- **宽限期**：同时接受新旧两个密钥，等旧 token 全部过期后停用旧密钥。需要维护一个「当前有效的密钥列表」——状态。
- **强制重登**：换密钥后所有 token 失效，用户重新登录。用户体验差但无状态。

Auth0（mastery/auth0.md）用 JWKS 端点优雅地解决了这个问题：公钥有 `kid`（Key ID），轮换时发新的 `kid`，验证方通过 JWKS 端点获取当前有效的公钥列表。但本质上，JWKS 端点本身就是一个有状态的服务——它维护着「当前哪些密钥有效」。

## 重新理解「无状态」

所以更准确的说法是：

> JWT 让 **token 验证**无状态，但完整的 **认证系统** 在生产中几乎必然有状态。

无状态的真正价值不是「零数据库」，而是**解耦**：

- **验证解耦**：API 服务器不需要连接用户数据库就能验证 token，这在微服务架构中意义重大
- **水平扩展**：任何新启动的服务实例只要有密钥就能验证，不需要预热缓存或同步状态
- **网关层验证**：可以在 API 网关统一做 token 验证，后端服务完全不需要关心认证

这是 JWT 的真实优势：不是消除状态，而是把状态从每次请求都需要的「热路径」上移开，放到低频的操作中（刷新、撤销、密钥轮换）。你的请求验证快了，因为不需要查库；但你的系统依然有状态管理，只是频次低了很多。

## 什么时候该承认有状态

如果你的业务需要以下任何一个，不要执着于「无状态」：

- 即时踢人（用户被封禁后 token 立刻失效）
- 实时权限变更（改了角色后立刻生效）
- token 中携带大量可变数据

这些场景下，session-based 认证可能反而更简单——服务端存状态、查状态，直截了当。JWT 的优势变成了劣势：你在「无状态」的框架上硬加了各种有状态的补丁，复杂度比直接用 session 还高。
