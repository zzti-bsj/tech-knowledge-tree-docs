# JWT 和 OAuth 2.0 到底是什么关系？

JWT 是一种 token **格式**，OAuth 2.0 是一种授权**协议**。它们不是竞争关系，不是替代关系，而是不同层面的东西——就像 JSON 是数据格式，REST 是 API 设计风格，两者经常一起出现但本质独立。

## 分层理解

把认证和授权的技术栈从上到下分层：

| 层 | 解决的问题 | 代表技术 |
|---|---|---|
| 授权协议 | 「我能访问你的什么资源？」 | OAuth 2.0 |
| 认证协议 | 「你是谁？」 | OpenID Connect |
| Token 格式 | 「凭证以什么形式传递？」 | JWT |

JWT 工作在最底层——它定义的是凭证的**物理形态**：一段 JSON 被 base64 编码后用密钥签名，变成一个字符串。它不关心这个字符串用来做什么。

OAuth 2.0 工作在最上层——它定义的是一个**交互流程**：用户授权 → 授权服务器发 token → 客户端拿 token 访问资源。它不关心 token 长什么样。

它们的交集是：OAuth 2.0 在 token 颁发环节，**经常选择** JWT 作为 token 的格式。但「经常」不等于「必须」——OAuth 2.0 的 token 可以是任何不透明字符串（比如一个 UUID 查询数据库），JWT 只是最流行的选择。

## 为什么会被混淆

混淆的根源在于：很多教程把「用 JWT 做登录认证」和「用 OAuth 2.0 做第三方授权」放在一起讲，因为实现层面它们共享同一套 token 签发和验证的代码。

但它们解决的是不同问题：

**JWT 的核心问题**（参见 README）：分布式系统中如何让服务器不依赖共享存储就能验证用户身份。答案是用签名验证替代服务端存储。

**OAuth 2.0 的核心问题**：如何让用户把自己在 A 系统的权限安全地委托给 B 系统，而不需要把密码给 B。比如「让「用微信登录」的第三方应用访问你的微信头像」，用户不需要把微信密码给第三方。

场景完全不同：JWT 解决「我是谁」，OAuth 2.0 解决「我允许你做什么」。

## OpenID Connect：缺失的桥梁

JWT 和 OAuth 2.0 之间有一个正式的桥梁：**OpenID Connect（OIDC）**。

OAuth 2.0 只管授权，不管认证。它发的 access_token 是给 API 用的，里面不包含用户身份信息（或者说不应该被客户端解析）。但很多场景你确实需要知道「这个用户是谁」。

OIDC 在 OAuth 2.0 之上加了一层：授权服务器除了发 access_token，还发一个 **id_token**——这个 token **必须是 JWT 格式**，里面包含用户身份信息（sub、name、email 等）。客户端解析 id_token 就知道用户是谁，用 access_token 去调 API。

这就是为什么 Auth0（mastery/auth0.md）同时发了 JWT 格式的 token——因为 Auth0 实现的是 OIDC 协议，JWT 在这里是 OIDC 规范要求的。

## 选型指南

| 场景 | 选择 | 原因 |
|---|---|---|
| 自己的应用，用户登录后调自己的 API | JWT（自管） | 你不需要授权协议，只需要认证 token |
| 第三方登录（微信/Google 登录） | OAuth 2.0 + JWT | 标准协议，社交平台都支持 |
| 企业 SSO | OIDC（OAuth 2.0 + JWT） | 需要同时解决认证和授权 |
| 微服务间内部通信 | JWT（自管） | 只需要服务间身份验证，不涉及用户授权 |

**一个常见的错误**：在只需要用户登录的场景中引入完整的 OAuth 2.0 流程。如果你的应用不需要第三方授权，直接用 JWT 签发 token 就够了（就像 pyjwt-fastapi.md 那样），不需要 OAuth 2.0 的授权码流程、redirect_uri 这些复杂性。
